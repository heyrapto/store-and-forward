# Edge Cases

This document describes edge cases in the messaging system, defining the expected behavior, how the architecture handles it, and how it is tested.

### 1. Message sent while sender is offline
- **Scenario**: A user types and sends a message, but their device is currently disconnected from the gateway.
- **Correct Behavior**: The message is queued locally. The UI shows a clock icon (⏱). When connectivity returns, messages are flushed in order.
- **System Handling**: The client maintains an outbox queue. Upon receiving the WebSocket `open` event, it flushes the outbox to the server.
- **Test**: Disconnect client WebSocket -> Send message -> Assert local queue length = 1 -> Reconnect -> Assert server receives message.

### 2. Recipient offline for 30 days
- **Scenario**: A message is sent to a device that does not connect for over 30 days.
- **Correct Behavior**: The message should expire. The sender will never see the delivery ticks (✓✓).
- **System Handling**: A TTL sweeper background job or database-level TTL removes stale delivery rows from the mailbox table.
- **Test**: Insert mock delivery row with timestamp -31 days -> Run sweeper -> Assert row is deleted.

### 3. Duplicate message delivery
- **Scenario**: The gateway pushes a message to the client, but the client's `ack` is lost due to a sudden disconnect. The gateway will resend it upon reconnection.
- **Correct Behavior**: The client should only display the message once. The server should gracefully accept the duplicate ack.
- **System Handling**: The client dedupes incoming messages by their UUID. `ack_device` on the server is idempotent (if the row is already marked delivered or deleted, it returns an OK status).
- **Test**: Server pushes same message twice -> Assert client UI shows one bubble. Client acks same message twice -> Assert server returns HTTP 200 both times.

### 4. Gateway crash mid-delivery
- **Scenario**: The server pushes a message over WS, but the gateway container crashes immediately before receiving the client's ack.
- **Correct Behavior**: No data loss. The client will reconnect to another gateway and receive the message again.
- **System Handling**: Since the ack wasn't processed, the delivery row in the DB remains pending. When the client reconnects to a surviving gateway, the new gateway drains the mailbox and re-sends the message.
- **Test**: Covered by the "Kill a gateway" integration test.

### 5. Slow/unresponsive device
- **Scenario**: A device is technically connected but the TCP window is full and it stops reading from the WebSocket.
- **Correct Behavior**: The gateway should drop the connection to protect server memory.
- **System Handling**: The gateway uses a bounded outbound channel for the WebSocket. If the channel blocks (N missed writes), the server forcibly closes the connection. The mailbox row stays pending.
- **Test**: Mock a slow client connection -> Bombard with messages -> Assert connection closed by server.

### 6. Clock skew between client and server
- **Scenario**: The sender's local device clock is 5 minutes in the future.
- **Correct Behavior**: The UI can display the client's time, but the server's time dictates the absolute truth for message ordering.
- **System Handling**: The `sent_at` timestamp is generated by the client (display only). The server attaches an authoritative `server_at` timestamp upon receipt.
- **Test**: Send message with future `sent_at` -> Assert `server_at` is current server time -> Assert sorting is by `server_at`.

### 7. Device reconnects before ack_device is received
- **Scenario**: Client receives a message, but disconnects *before* sending the HTTP ack. Client reconnects immediately.
- **Correct Behavior**: The message is resent to the client; the client dedupes it.
- **System Handling**: The client passes its last known sequence cursor during reconnection. The server queries all pending messages > cursor. 
- **Test**: Client receives msg -> Client closes WS -> Client connects -> Server sends same msg -> Client dedupes.

### 8. Large group fan-out
- **Scenario**: A message is sent to a group with 10,000 members.
- **Correct Behavior**: The server should not block the sender or run out of memory. All members should eventually receive the message.
- **System Handling**: A worker pool bounds concurrency. The fan-out process inserts delivery rows in a single batch transaction to avoid excessive DB round-trips.
- **Test**: Send message to group (N=10k) -> Assert server handles within bounded memory -> Assert 10k rows inserted.

### 9. Redis down (Episode 3)
- **Scenario**: The Redis pub/sub cluster becomes unavailable.
- **Correct Behavior**: Gateways gracefully degrade. Cross-gateway instant routing fails, but local processing continues.
- **System Handling**: Gateways catch Redis connection errors. They fall back to saving messages to the DB without pub/sub triggers. Mailboxes are still drained when clients poll/reconnect. Gateways still handle their local connections.
- **Test**: Stop Redis -> Send message between two clients on different gateways -> Assert message delivered eventually via poll.

### 10. SQLite busy/locked
- **Scenario**: High concurrent writes to the shared SQLite file cause locking.
- **Correct Behavior**: Operations should retry and eventually succeed or gracefully fail.
- **System Handling**: SQLite is configured in WAL (Write-Ahead Log) mode with a generous busy timeout (5s). If it fails, the API returns a 503. Swapping to Postgres eliminates this.
- **Test**: Concurrently write 1000 messages -> Assert 0 DB lock errors (handled by WAL).

### 11. Two devices with same device_id
- **Scenario**: A user somehow runs two instances of the app with the exact same device ID.
- **Correct Behavior**: Only one active session is allowed to prevent routing conflicts.
- **System Handling**: When the second connection sends its `hello` frame, the gateway detects an existing session for that ID and gracefully terminates the older connection.
- **Test**: Connect Client A -> Connect Client B (same ID) -> Assert Client A is disconnected.

### 12. Message to a device that was deleted
- **Scenario**: A client tries to send a message to a device ID that has been purged from the system.
- **Correct Behavior**: The API rejects the message.
- **System Handling**: The `send_message` use case validates that the recipient device exists in the database. Returns a `404 Not Found` or `400 Bad Request` to the sender.
- **Test**: Send message to "fake-id" -> Assert API returns error -> Assert no mailbox row created.
